# Mejoras al modelo de datos

Este documento recoge las propuestas de mejora identificadas sobre el esquema actual de GEMA. Cada propuesta incluye el problema que resuelve, qué tablas afecta y un borrador del cambio en formato tabular.

> [!NOTE]
> Estas mejoras están consolidadas en la [propuesta v0.1](/docs/analisis/database/propuesta-v0.1), que presenta el esquema completo con todos los cambios aplicados.

---

## 1. Auditoría y trazabilidad

El modelo actual tiene una sola tabla `auditoria_sistema` que registra acciones genéricas. Eso no nos dice qué valor tenía un campo antes de cambiar, ni por qué cambió el estado de un activo. La propuesta es separar la auditoría en tablas especializadas.

**Qué cambia:**

- `logs_estados_activos` ya existe pero se mantiene como está
- Se agrega `logs_estados_ordenes_trabajo` para rastrear transiciones de OT
- Se renombra `auditoria_sistema` a `auditorias_sistema` (cambio de nombre en plural)
- Se crea `auditorias_cambios` para registrar cambios a nivel de campo en cualquier tabla

**Qué tablas afecta:** `auditoria_sistema`, `logs_estados_activos`, `ordenes_trabajo`

## 2. Multimoneda con histórico de tasas

El esquema actual guarda un valor numérico y un código de divisa (`USD`, `VES`). Si la tasa de cambio varía, los reportes históricos pierden sentido porque no hay forma de reconstruir la conversión original.

La solución es registrar el monto en la divisa original y su equivalente en la moneda base del sistema, junto con la tasa que se usó en ese momento.

**Qué cambia:**

- Se crea la tabla `tasas_cambio` para guardar tasas históricas
- Cada campo monetario se duplica: `*_original` y `*_base`
- Se agrega `tasa_cambio_id` como referencia a la tasa aplicada
- Se agrega `updated_at` a las tablas que ganan campos nuevos

**Qué tablas afecta:** `activos`, `ordenes_trabajo`, `inventario_repuestos`, `entradas_inventario`

## 3. Eliminación de redundancia en planes preventivos

El diseño actual tiene dos campos que dicen lo mismo: `frecuencia` (un enum como `mensual`) e `intervalo_dias` (un número). Si un plan dice "mensual" pero el intervalo marca 45 días, el backend no sabe a cuál hacerle caso.

La propuesta es eliminar el enum `frecuencia_tipo` y dejar `intervalo_dias` como única fuente de verdad. La interfaz puede derivar la etiqueta visual ("mensual", "semanal") del número, no al revés.

**Qué cambia:**

- Se elimina el campo `frecuencia` de `planes_mantenimiento`
- `intervalo_dias` pasa a ser `not null`
- Se crea `planes_ejecuciones` para vincular cada plan con las OT que generó

**Qué tablas afecta:** `planes_mantenimiento`

**Estado actual:**

| Enum | Valores |
|---|---|
| `frecuencia_tipo` | `diaria`, `semanal`, `quincenal`, `mensual`, `trimestral`, `semestral`, `anual` |

## 4. Firmas digitales en órdenes de trabajo

El campo `validado_gerencia` es un booleano que solo dice si alguien aprobó la orden. No dice quién ni cuándo. Para auditoría necesitamos saber exactamente quién autorizó el gasto.

La propuesta es reemplazar el booleano por una referencia al usuario que firma y un timestamp con la fecha de aprobación.

**Qué cambia:**

- Se elimina `validado_gerencia` de `ordenes_trabajo`
- Se agrega `validado_por_id` (ref a `usuarios.id`)
- Se agrega `fecha_validacion`
- Se agrega soporte multimoneda a los campos de costo (ver propuesta 2)
- Se renombra `reportes_falla` a `reportes_fallas` (consistencia en plural con las demás tablas)

**Qué tablas afecta:** `ordenes_trabajo`, `reportes_falla`

**Estado actual:**

## 5. Estandarización de integridad y metadatos

El esquema actual usa `text` libre para campos como el tipo de ubicación o el módulo de permisos. Si alguien escribe "Sede" en un registro y "sede" en otro, el filtro los trata como valores distintos. También faltan timestamps automáticos en varias tablas.

La propuesta es convertir esos campos de texto a enums nativos y agregar `created_at` / `updated_at` con `now()` por defecto en todas las tablas.

**Qué cambia:**

- `tipo` en `ubicaciones` pasa de `varchar` a `enum tipo_ubicacion`
- `modulo` en `permisos` pasa de `varchar` a `enum modulo_permiso`
- Campos `text` de longitud corta pasan a `varchar`
- `articulos_catalogo` gana `nombre` (varchar not null) y `descripcion` (text) para identificar mejor cada artículo del catálogo
- Todas las tablas ganan `created_at` y `updated_at` con default `now()`

**Qué tablas afecta:** `usuarios`, `roles`, `permisos`, `ubicaciones`, `categorias_articulos`, `articulos_catalogo`, `proveedores`

**Estado actual (ejemplo con `usuarios` y `ubicaciones`):**

## 6. Business Intelligence y alertas proactivas

El modelo actual no tiene tablas de KPIs ni alertas. Para ver el MTBF de un activo hay que recorrer todas las órdenes de trabajo y calcular en caliente, lo que degrada el rendimiento con muchos registros.

La propuesta es crear tablas de métricas mensuales precalculadas y una tabla de alertas para avisos de stock bajo o planes vencidos.

**Qué cambia:**

- Se crea `alertas` con campos polimórficos (`entidad_id`, `entidad_tabla`) para vincular a cualquier tabla
- Se crea `kpis_activos_mensuales` con índice único por `(activo_id, anio, mes)`
- Se crea `kpis_tecnicos_mensuales` con índice único por `(tecnico_id, anio, mes)`

**Qué tablas afecta:** nuevas tablas, no modifica las existentes

**Estado actual:** no implementado

**Propuesta:**

| Enum | Valores |
|---|---|
| `tipo_alerta` | `stock_bajo`, `vencimiento_plan`, `otra` |
| `estado_alerta` | `pendiente`, `resuelta`, `archivada` |

<br />
